# ERD 수정 검토 기록

이 문서는 `ERD_v6.md`에서 `ERD_v7.md`로 변경하며 반영한 데이터 모델 수정사항과 설계 판단을 기록한 변경 이력이다. 배경은 `docs/draft_signup_mentoring_feedback_v1.md` 참고.

## 1. `users`에 `birthday`/`address`/`special_notes` 추가 — 반영 완료

리뷰 코멘트: "회원가입 인적사항으로 이름·주민번호·주소·아이디·비밀번호·특이사항·연결되는 ID·보호자 연락처를 받고 싶다."

결정: 주민등록번호는 개인정보보호법상 고유식별정보로 원칙적 수집 제한 대상이라 제외하고, 본인확인 목적은 `birthday`(생년월일)로 대체한다(사용자 확정). `주소`·`특이사항`은 법적 리스크가 없어 그대로 추가한다. `아이디`는 별도 필드를 만들지 않고 기존 이메일/전화번호 로그인을 유지하기로 확정했다(사용자 확정).

```text
users
- birthday date nullable        // 추가, 주민번호 대체
- address string nullable       // 추가
- special_notes string nullable // 추가, 특이사항
```

## 2. "연결되는 ID"/"보호자 연락처" — 신규 테이블 없이 기존 `care_relation_invitations` 재사용 — 반영 완료

리뷰 코멘트: "인적사항에 연결되는 ID, 보호자 연락처를 포함해달라."

결정(사용자 확정: 보호자 연락처 입력 시 자동 초대 발송): 새 컬럼이나 테이블을 추가하지 않는다. `role=medication_subject` 가입 시 입력한 보호자 연락처를 API 계층에서 기존 `care_relation_invitations.invited_phone`에 그대로 사용해 자동으로 초대를 생성한다. "연결되는 ID"는 로그인 아이디 개념 자체가 없어(이메일/전화번호 로그인 유지) 별도 필드로 만들지 않고 동일한 전화번호 기반 초대로 흡수한다. ERD 스키마 변경 없음 — API 명세서 v6에서 동작만 정의한다.

## 3. (후속 수정) 요구사항 추적표에 REQ-045~049 누락 — 반영 완료

리뷰 코멘트: 서브에이전트 3라운드 교차 검토에서 발견 — "요구사항 추적" 표가 REQ-040~044에서 끝나 있고, `birthday`/`address`/`special_notes`는 여전히 REQ-001 행에 남아 있어 요구사항_정의서_v7.xlsx가 새로 만든 REQ-045~049와 ERD 사이의 연결이 끊겨 있었다.

결정: REQ-001 행에서 `birthday`/`address`/`special_notes`를 제거하고, REQ-045(인적사항 확장)·REQ-046(보호자 자동초대)·REQ-047(오타 제안)·REQ-048(챗봇 연결)·REQ-049(앱 진입화면 정책) 행을 추적표에 추가했다. 또한 개인/단체 회원가입 구분이 이번 버전 범위에서 제외되었다는 사실이 ERD 본문에는 전혀 남아 있지 않아, "핵심 제약과 조회 규칙"에 범위 제외 주석 한 줄을 추가했다.

## 팀에 설명할 핵심 결정

1. 주민번호는 채택하지 않는다. 현재 설계가 의도적으로 복구 불가능한 해시만 남기는 개인정보 최소화 원칙을 지키고 있어, 원본 고유식별정보 수집은 이 원칙과 정면 충돌하기 때문이다.
2. "연결되는 ID"·"보호자 연락처"는 두 개의 별도 필드로 만들지 않고 기존 초대 메커니즘(전화번호 기반, 가입 여부 무관 동일 동작) 하나로 통합했다. 로그인 식별자를 이메일/전화번호로 유지하기로 한 결정과 일관성을 맞추기 위함이다.
3. "개인/단체 회원가입 구분"은 이번 버전업 범위에서 제외했다(사용자 확정) — `account_type`/`organizations` 테이블 설계는 별도 논의 후 진행한다. `docs/draft_signup_mentoring_feedback_v1.md`에 백로그로 남겨둔다.
4. 이번 버전도 문서(ERD·API 명세서·요구사항 정의서) 변경만 반영하며, `app/models/users.py`는 이미 ERD와 크게 어긋난 상태(별도 감사 결과, `docs/revision_logs/API명세서/API명세서_v4_to_v5_revision_log.md` 및 후속 코드 정합성 작업 참고)이므로 이번 필드 추가도 코드에는 아직 반영되지 않았다.
