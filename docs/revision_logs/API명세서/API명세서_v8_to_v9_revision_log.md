## PR 전 3라운드 서브에이전트 감사(2026-07-21)로 발견·수정된 오류

최초 v9 작성 초안을 PR로 올리기 전, 별도의 3개 서브에이전트가 각 문서를 코드와 대조해 독립적으로 재검증했다. API명세서_v9에서 다음 오류가 발견되어 이 문서에 이미 반영했다:
- **6절(챗봇) 인가 서술 오류(가장 심각)**: 초안이 "chat_router는 여전히 인가 미적용"이라고 썼으나, 실제로는 2026-07-14부터 4개 엔드포인트 전부 `Depends(get_current_actor)`+`require_actor_patient_access`가 적용돼 있었다(초안이 v8의 오래된 서술을 검증 없이 이어받은 것). 상단 인가 요약, 6절 본문, `GET /chat/questions`의 누락된 `patient_id` 파라미터를 모두 정정.
- **보호자→환자 초대 "비밀번호 필수" 서술 오류**: 실제 committed dev 코드(`care_router.py:accept_invitation`)에는 비밀번호 필수 검증이 없다 — 작성자가 자신의 미커밋 stash 작업을 dev 상태로 착각해 기재했던 오류.
- `POST .../check` 요청 바디의 `confirmed_by_caregiver_id`(서버가 자체 계산, 클라이언트 입력 아님), `POST /records`/`/records/manual`/`/records/{id}/confirm`의 존재하지 않는 최상위 `cached`/`cache_expires_at` 필드, `POST /rag/test/{record_id}`의 잘못된 응답 형태, `backend/dependencies.py`(실제는 `backend/core/dependencies.py`) 경로 오타, `/invitations`의 `organization` relation_type 오기재를 모두 정정.
- `patient_medications_router.py`(2026-07-14 등록)가 조사 범위 밖이라 여전히 미문서화 상태임을 "범위 밖" 절로 명시.

## Round 2(문서 간 정합성) 감사로 추가 발견·수정된 오류

- **REQ-035 파고들지 못한 잔여 오류**: Round 1에서 ERD·요구사항_정의서는 purge 배치 존재를 확인해 정정했으나, API명세서_v9의 1절 본문 자체는 놓쳐서 "실행 로직 유무를 확정하지 못했다"는 예전 문구가 그대로 남아 3개 문서가 서로 모순됐다 — Round 2 감사로 발견, 정정 완료.
- **REQ-037/REQ-058 번호 중복(가장 심각한 발견)**: "보호자→환자 초대" 기능을 API명세서·ERD 양쪽에서 "REQ-037"로 표기하고 있었으나, 요구사항_정의서의 REQ-037은 이미 복약 여부 기록(medication_records)을 가리키는 별개 번호로 확정돼 있었다 — 같은 번호가 두 무관한 기능을 가리키는 상태였다. 요구사항_정의서_v9에 REQ-058(보호자, 완료)을 신설하고 API명세서·ERD의 해당 참조를 전부 REQ-058로 정정했다.
- **REQ-049 상태어 불일치**: API명세서가 "부분 구현"으로, ERD·요구사항_정의서가 "확인필요"로 서로 다른 상태어를 쓰고 있었다 — API명세서를 "확인필요"로 통일.

## 남은 후속 확인 필요 항목

- 회원 탈퇴(REQ-035) 30일 경과 후 실제 영구 삭제 배치(purge) 실행 로직 유무 — 이번 조사에서 코드 정적 분석만으로는 확정하지 못함.
- `care_router`의 prefix 부재(RESTful 일관성) — v8부터 지적됐으나 이번 버전에서도 조치하지 않음.
- API명세서에 REQ 번호를 직접 인용하지 않는 29개 REQ에 대한 매핑표 — 범위 제외.
