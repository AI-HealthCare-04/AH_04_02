# API 명세서 수정 검토 기록

이 문서는 `API명세서_v5.md`에서 `API명세서_v6.md`로 변경하며 반영한 수정사항과 설계 판단을 기록한 변경 이력이다. 배경은 `docs/draft_signup_mentoring_feedback_v1.md` 참고.

## 결론 요약

| 항목 | 판단 | API 수정 방향 |
|---|---|---|
| 회원가입 인적사항(주민번호 등) | 부분 적용 | 주민번호 제외, `birthday`/`address`/`special_notes`만 `/auth/register`에 추가 |
| 가입 시 보호자 연락처 | 적용 | `guardian_phone`으로 받아 자동 초대(`invitation_id` 응답 포함) |
| OCR 저신뢰 확인 후 오타 안내 | 적용 | `PATCH .../medications/{medication_id}` 응답에 `typo_suggestion` 추가 |
| 저신뢰 확인 후 챗봇 연결 | 적용(문서 수준) | 기존 `/chat` 스키마 유지, 가이드 존재 시 UI에서 `guide_result_id`로 진입하도록 규정 |
| 앱 최초 실행 화면 정책 | 적용(문서 수준) | 별도 API 없이 클라이언트 동작 규약으로 명시 |
| 개인/단체 회원가입 구분 | 보류 | 이번 버전 범위 제외 |

## 1. 회원가입 인적사항 확장 반영 완료

리뷰 코멘트: "인적사항 - 이름, 주민번호, 주소, 아이디, 비밀번호, 특이사항, 연결되는 ID, 보호자 연락처."

결정:
- `birthday?`(생년월일, 주민번호 대체), `address?`, `special_notes?`를 `POST /auth/register` 요청에 추가하고 `GET /users/me` 응답에도 노출한다.
- "아이디"는 별도 필드를 만들지 않고 기존 `email_or_phone` 로그인을 유지한다(사용자 확정).
- "연결되는 ID"·"보호자 연락처"는 `guardian_phone`(+선택적 `guardian_relation_type`) 하나로 통합한다. 가입 시 이 값을 보내면 서버가 `POST /care-relations/invitations`와 동일한 로직으로 초대를 자동 생성하고 응답에 `invitation_id`를 포함한다. 상대가 미가입 상태일 수 있으므로 관계 승인은 기존 2절 절차(`.../accept`)를 그대로 따른다 — 가입 즉시 `care_relations`가 생기는 것은 아니다.

## 2. OCR 저신뢰 확인 — 오타 안내·챗봇 연결 반영 완료

리뷰 코멘트: "OCR 했을 때 안되면 스스로 입력하게 하고, 오타나면 오타입니다 확인해달라고 한 다음, 트러블이 있으면 챗봇이랑 대화하기를 누를 수 있는 UI 구조."

결정:
- 자가입력 자체는 기존 `PATCH /medical-records/{record_id}/medications/{medication_id}`로 이미 지원되므로 스키마를 유지한다.
- 오타 안내를 위해 응답에 `typo_suggestion?`을 추가한다 — 입력한 `drug_name`이 약물명 사전과 정확히 일치하지 않을 때 가장 유사한 후보를 반환하는 응답 전용 값(저장하지 않음)이다.
- 챗봇 연결은 `/chat` 요청 스키마를 바꾸지 않는다. 저신뢰 확인 시점에는 아직 `guide_results`가 없을 수 있으므로, 가이드가 이미 생성된 경우에만 `GET .../guide`의 `guide_result_id`로 챗봇 진입 버튼을 노출하도록 UI 규칙으로 문서화한다. 가이드가 없는 상태에서 챗봇을 열 수 있게 스키마를 확장하는 대안도 검토했으나, 확인→가이드 생성 흐름상 대부분의 경우 확인 시점에 가이드가 이미 존재해 스키마 확장이 불필요하다고 판단했다.

## 3. 앱 최초 실행 화면 정책 반영 완료

리뷰 코멘트: "어플을 키면 회원가입 창이 나온다."

결정: 별도 API를 추가하지 않고 클라이언트 동작 규약으로 명시한다 — 유효한 `refresh_token`이 있으면 자동 로그인 후 홈 화면, 없거나 만료되면 회원가입 화면을 기본으로 하되 로그인 화면으로 이동하는 링크를 제공한다.

## 4. 개인/단체 회원가입 구분 — 보류

리뷰 코멘트: "개인인지 단체인지 선택 후 그에 맞게 회원가입을 하게 하고 싶다."

결정(사용자 확정): 이번 버전 범위에서 제외한다. `account_type`(individual/organization) 필드와 `organizations` 테이블 설계가 필요하며 별도 논의 후 진행한다.

## 5. (후속 수정) 섹션 헤더에 신규 REQ 번호 누락 — 반영 완료

리뷰 코멘트: 서브에이전트 3라운드 교차 검토에서 발견 — 1절(인증·사용자)이 REQ-045/046/049 내용을 담고 있으면서도 헤더에는 예전 REQ 번호만 표기되어 있었고, 4절(진료기록·OCR)은 REQ-047, 6절(챗봇)은 REQ-048을 각각 누락했다.

결정: 세 섹션 헤더에 해당 REQ 번호를 추가했다(`## 1. 인증·사용자 (REQ-001, REQ-031, REQ-035, REQ-039, REQ-045, REQ-046, REQ-049)`, `## 4. 진료기록·OCR (REQ-008~011, REQ-023~024, REQ-047)`, `## 6. 챗봇 (REQ-021~022, REQ-048)`). ERD_v7.md의 "요구사항 추적" 표에도 동일한 REQ 행을 추가해 두 문서의 추적성을 맞췄다(`docs/revision_logs/ERD/ERD_v6_to_v7_revision_log.md` 3절 참고).

## 팀에 설명할 핵심 결정

1. 주민번호는 채택하지 않는다 — 개인정보보호법상 고유식별정보 수집 제한과 현재 설계의 개인정보 최소화 원칙(복구 불가능한 해시만 보존) 때문이다. `birthday`로 대체했다.
2. "아이디" 필드를 신설하지 않고 이메일/전화번호 로그인을 유지하기로 한 결정에 맞춰, "연결되는 ID"도 계정 식별자 직접 입력 방식 대신 전화번호 기반 자동 초대(`guardian_phone`) 하나로 통합했다.
3. 저신뢰 OCR 확인 후 챗봇 연결은 스키마를 확장하지 않고 기존 `guide_result_id` 기반 `/chat`을 그대로 쓰도록 UI 규칙만 추가했다 — 불필요한 스키마 확장을 피했다.
4. 개인/단체 구분은 설계 결정 사항이 많아(단체의 정의, 로그인 단위, 추가 서류 등) 이번 스프린트에서 확정하지 않고 백로그로 남긴다.
5. 이번 버전도 문서 변경만 반영하며 실제 FastAPI 코드(`app/apis/v1/auth_routers.py` 등)는 아직 ERD/API 문서와 전면적으로 어긋난 상태라 별도 코드 정합화 작업이 선행되어야 한다.
