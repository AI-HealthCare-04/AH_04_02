# 요구사항 정의서 수정 검토 기록 — v8 → v9

> 버전: v8 → v9 · 날짜: 2026-07-21 · 작성자: 김영혜

배경: (1) `요구사항정의서_API명세서_정합성검토.docx`(권순현, 2026-07-15) 지적사항 반영, (2) PR #56/#59/#60/#61/#62 병합으로 dev 실제 구현 현황이 크게 갱신됨, (3) 2026-07-17 팀 회의 결정사항(메뉴 구조, 모바일 우선, 복약/알림 흐름) 반영. 시트 구조(공통/복약관리대상자/보호자/지원인력 4개 그룹 + 참고 시트)는 v8에서 확정한 것을 그대로 유지하고, 이번 개정은 셀 단위 정정과 신규 REQ 추가만 수행했다.

## 1. 정합성 검토 지적사항 반영 — "방향 자체가 반대인 항목" 3건 정정

- **REQ-009(OCR 엔진)**: "EasyOCR로 완료"라고 서술해 실제(CLOVA OCR)와 정반대로 기록돼 있었다. 이 상태로 인수 테스트를 하면 정상 동작 중인 CLOVA OCR을 오히려 실패로 판정하게 되는 위험이 있었다 — v9에서 CLOVA 기준으로 상세내용·인수조건을 전부 정정했다.
- **REQ-011(OCR 신뢰도 임계값)**: "신뢰도 0.80 미만만 review_required"로 서술했으나 실제로는 신뢰도와 무관하게 항상 review_required — "저신뢰만 확인"에서 "전부 확인"으로 정책이 바뀐 사실을 반영해 정정했다.
- **REQ-032(면책 고지)**: "완료"로 서술했으나 API명세서_v7·ERD_v8은 이미 2026-07-13에 "부분"(disclaimer가 API 응답 필드가 아니라 프론트 하드코딩)으로 정정돼 있었다 — 요구사항_정의서_v8만 이 정정을 누락하고 있었던 것을 v9에서 바로잡았다.

## 2. 정합성 검토 지적사항 반영 — 용어·엔드포인트 불일치

- **REQ-046**: 상세내용이 존재하지 않는 테이블명 "care_relation_invitations"를 언급하고 있었다 — 실제 테이블명 `invitations`로 정정.
- **REQ-045**: 구현 판단 근거가 언급하던 "GET /users/me"는 실재하지 않는 경로였다 — 실제로는 `GET /monitoring/patients`·`GET /monitoring/caregivers`가 그 역할을 함을 명시.
- **REQ-002**: "토큰이 해시가 아닌 원문 저장 여부는 재확인 필요"라는 미확정 상태였다 — 2026-07-21 코드 재확인으로 `token_hash`(해시) 저장이 확인돼 정정.

## 4. 2026-07-17 회의 결정사항 반영 — 자가진단 목적 폐기와 식사시간 대체

**배경**: 사용자(팀) 확인 결과, 자가진단(REQ-005/006/007)은 원래 care_level(제3자 도움 필요 여부) 판단 근거를 제공하려는 목적이었으나, 2026-07-17 회의에서 **이 목적 자체를 서비스 방향에서 제외하기로 결정**했다. 다만 이 온보딩 화면의 구조(단계별 입력 UI)는 그대로 벤치마킹해, 복약 알림 설정 시 참고할 수 있는 **식사시간**을 물어보는 것으로 목적을 교체했다.

- **REQ-005/006/007**: "완료" → **"보류"**로 재분류. 백엔드 API는 코드에 남아 정상 동작하지만(그래서 "미구현"이 아니다), 이를 만드는 프론트 화면 자체가 없고(전수 조사로 확인, `createAssessment` 호출부가 프론트 어디에도 없음) 이 방향으로 더 개발하지 않기로 결정됐으므로 "보류"가 정확하다.
- **REQ-007a/026c**: 완료/부분 상태는 유지하되, "이 REQ들이 참조하는 care_level은 자가진단 부재로 항상 independent로 폴백되어 third_party_needed 분기가 실질적으로 도달 불가능하다"는 사실을 근거에 명시했다.
- **REQ-051(신규)**: 식사시간 입력(`MealTimeCheck.tsx`, 회원가입 직후 온보딩)을 "부분 구현"으로 신설했다 — 입력·저장(`PUT /patients/{id}/meal-times`)은 완료됐으나, 알림 스케줄러나 가이드 생성 로직 어디에도 이 값을 실제로 읽어 활용하는 코드가 없어 "수집만 되고 활용되지 않는 데이터" 상태임을 명시했다.

## 5. 2026-07-17 회의 결정사항 반영 — 모바일 우선 설계(최우선 순위)

**REQ-054(신규)**: 팀이 "매우 시급(VERY URGENT)"으로 지정한 모바일 반응형 설계 요구사항을 신설했다. 우선순위는 High로 하되 회의에서 지정한 긴급도를 근거란에 그대로 기록했다. 프론트 전수 조사 결과를 근거로 "부분 구현"으로 판정했다 — `Dashboard.tsx`/`Login.tsx`/`NavBar.tsx`는 이미 모바일 우선(작은 화면이 기본, `sm:`/`lg:`로 확장) 원칙을 따르고 있으나, `Records.tsx`/`MedGuide.tsx`/`Chat.tsx`/`MyPage.tsx`/`SignUp.tsx`는 반응형 브레이크포인트가 거의 없는 고정폭 레이아웃에 가깝다. 카드형·터치블록 UI는 일부 화면(회원가입 유형 선택, 대시보드 복용확인 버튼, 식사시간 규칙성 토글)에는 이미 있으나 전체 화면에 일관되게 적용돼 있지는 않다.

## 6. 2026-07-17 회의 결정사항 반영 — 메뉴 구조 개편

**REQ-055(신규, 공통)**: "전체메뉴 삭제 + 모바일 햄버거 메뉴 + 메뉴명 변경(처방전 등록→처방등록, 오늘의 복약→복약기록 통합, 복약일정→알림내역)"을 하나의 요구사항으로 신설했다. **중요한 발견**: 모바일 햄버거 메뉴는 회의 이전부터 `NavBar.tsx`에 이미 구현돼 있었다(코드 조사로 확인) — 팀이 이 사실을 모르고 "모바일에서는 햄버거 메뉴로 동작해야 한다"고 요청했을 가능성이 있어, 이미 구현된 부분과 아직 안 된 부분(전체메뉴 삭제, 메뉴명 변경, 재배치)을 명확히 구분해 중복 개발을 방지했다.

**REQ-056(신규, 보호자)**: 메뉴 구조 개편의 일부로, 보호자 로그인 시 상단 메뉴에 보호자 전용 기능(환자 관리 등)이 노출돼야 한다는 요구사항을 별도로 신설했다 — 코드 조사 결과 `NavBar.tsx`가 로그인한 사용자의 역할(환자/보호자)을 전혀 구분하지 않는 고정 메뉴 배열이라, 이 요구사항은 REQ-055와 함께 처리해야 하는 별개의 미구현 항목이다.

## 7. 2026-07-17 회의 결정사항 반영 — 알림·복약기록 흐름

**REQ-057(신규, 공통)**: 복약 알림(`notification_logs`)과 복약 기록(`medication_records`)의 관계를 명문화했다. 회의에서 요청한 "'먹었어요/안 먹었어요' 화면이 알림 이후 자연스럽게 뜨도록 흐름 변경"은 **부분 구현으로 판정**했다 — 두 테이블 간의 데이터 관계 자체는 PR #62로 이미 구현돼 있지만, 요청하신 "UX 흐름 변경"(알림을 눌러야 확인 화면으로 진입)은 실제 push 알림 인프라(REQ-026a의 미구현 부분) 없이는 성립할 수 없어, 현재는 알림과 무관하게 대시보드에 상시 노출되는 구조로 남아 있다.

## 8. 이미 구현돼 있었으나 문서화 누락이던 기능 — REQ 신설

- **REQ-052(신규)**: 함량에 "/"가 들어가는 복합제 표기(예: 5/50mg) 인식 — `parsing_rules.py` 재확인 결과 이미 처리되고 있었다. "완료"로 신설.
- **REQ-053(신규)**: 약효분류(drug_class)는 필수 입력이 아니라 선택 정보 — `records_router.py`/`ocr_router.py` 재확인 결과 이미 그렇게 동작하고 있었다. "완료"로 신설.

이 두 항목은 회의에서 "이렇게 만들어달라"고 요청받았으나, 코드 조사 결과 이미 구현이 완료돼 있어 별도 개발 없이 문서 신설만으로 충족했다.

## 9. PR 전 3라운드 서브에이전트 감사(2026-07-21)로 발견·수정된 오류

v9 초안을 PR로 올리기 전, 3개 서브에이전트가 각 문서를 코드와 대조해 독립적으로 재검증했다. 요구사항_정의서_v9에서 다음이 발견돼 수정했다:

- **REQ-030/031/REQ-022(챗봇 이력, 3개 시트) chat_router 인가 오류**: "chat_router는 여전히 인가 미적용"이라는 서술이 6곳(공통 REQ-030/031, 복약관리대상자·보호자·지원인력 REQ-022)에 반복돼 있었다 — 실제로는 2026-07-14부터 인가가 적용돼 있었다(API명세서_v9와 동일 오류, 근본 원인은 v8의 오래된 서술을 검증 없이 이어받은 것). REQ-031을 완료로 승격.
- **REQ-006(보호자·지원인력 시트) 누락 수정**: REQ-005/007을 "보류"로 내리면서 같은 자가진단 흐름의 일부인 REQ-006(보호자·요양보호사의 체크리스트 입력)은 실수로 "완료"로 남겨져 있었다 — 용어집의 "자가진단 — REQ-005/006/007 보류"라는 자체 서술과도 모순되는 누락이었다. 두 시트 모두 "보류"로 정정.
- **REQ-005 역사적 서술 오류**: "자가진단 입력 화면(Check.tsx)은 한 번도 만들어진 적이 없다"는 틀렸다 — v8 작성 시점엔 실제로 존재했고, 2026-07-15(회의보다 이틀 앞서) 진입 경로가 없는 고아 화면이라는 이유로 이미 삭제됐다. "07-17 회의가 화면을 없앴다"가 아니라 "화면은 그 전에 이미 없어졌고, 회의는 목적 자체를 폐기하기로 결정했다"로 정정.
- **REQ-035 purge 배치 "미확정" 오류**: `backend/scripts/purge_expired_accounts.py`가 이미 구현·테스트돼 있음을 확인 — "확정 못함"을 "존재하나 자동 스케줄링은 아님"으로 정정.
- **REQ-046 인수조건·용어집 잔존 오류**: 상세내용은 이미 실제 테이블명 `invitations`로 정정돼 있었으나, **인수조건** 컬럼과 **용어집**의 `guardian_phone` 항목에는 존재하지 않는 `care_relation_invitations`라는 이름과 "자동 발송된다"는 현재형 표현(REQ-046은 미구현인데도)이 그대로 남아 있었다 — 모두 정정.
- **REQ-047(3개 시트) 상세내용 경로 오류**: 상세내용이 존재하지 않는 `/medical-records/{record_id}/medications/{medication_id}` 경로를 언급했다(구현 판단 근거는 처음부터 올바른 `/records/...`였음) — 실제 `records_router.py` prefix인 `/records`로 통일.
- **REQ-055/REQ-050 minor 정정**: REQ-055의 "NAV_ITEMS 라벨이 v8 그대로"라는 근거가 부정확했다(2026-07-19에 한 차례 이미 변경됨, 다만 목표 명칭으로는 아직 안 바뀜 — 결론은 그대로 유효). REQ-050(지원인력)의 `models.py` 줄번호 인용이 코드 변경으로 밀려 있어 정정.

## 10. Round 2(문서 간 정합성)·Round 3(완전성) 감사로 추가 발견·수정된 오류

- **REQ-058(보호자 시트) 신설**: API명세서·ERD가 "보호자→환자 초대" 기능을 "REQ-037"로 표기하고 있었는데, 요구사항_정의서의 REQ-037은 이미 복약 여부 기록을 가리키는 별개 번호였다 — 번호 중복을 해소하기 위해 REQ-058(보호자, 완료)을 신설했다.
- **`핵심 흐름` 시트가 Round 1 수정에서 누락돼 있었음**: 이 시트는 REQ 행과 별개로 5개 흐름을 서술식으로 설명하는데, Round 1에서 고친 내용(EasyOCR→CLOVA, 신뢰도 임계값, 자가진단 보류, 교육관리 미구현, REQ-046 자동초대 미구현)이 전혀 반영되지 않아 다른 시트의 정정 내용과 정면으로 모순됐다(Round 3 완전성 감사로 발견) — 구현 상태 컬럼을 신설하고 각 흐름 서술에 보류/미구현 캐비어트를 추가해 정정했다.
- **User Story "그래야"(so-that) 절 누락**: 공통 시트 10개 행(REQ-026a/c/d, 030, 031, 032, 035, 039, 045, 049)이 "Who+What"만 있고 "So-that"이 빠져 있어 사용자 스토리 형식 요건을 완전히 충족하지 못했다 — 전부 보완.

## 팀에 설명할 핵심 결정

1. **자가진단(REQ-005/006/007)의 "보류"는 새로운 상태값이다** — 기존 완료/부분/미구현/확인필요 4단계에 "목적 자체가 폐기됐다"는 경우를 표현할 수 없어 이번에 도입했다. "미구현"과 구분되는 이유는, 미구현은 "아직 안 만들었지만 계획엔 있다"는 뜻이고 보류는 "만들 계획 자체가 없다"는 뜻이기 때문이다.
2. **REQ-051(식사시간)은 REQ-005(자가진단)를 대체하는 게 아니라 완전히 별개 기능이다** — 화면 구조만 재사용했을 뿐 목적·데이터·저장 위치가 다르므로 혼동하지 않도록 REQ 번호를 분리했다.
3. **REQ-054(모바일)는 이번 버전에서 가장 우선순위가 높은 항목이다** — 회의에서 지정한 긴급도(VERY URGENT)를 그대로 우선순위 컬럼에 반영했다.
4. **REQ-055(메뉴 개편)에서 "모바일 햄버거 메뉴"는 이미 구현돼 있었다** — 팀이 요청한 내용 중 일부는 이미 완료 상태이므로, 실제 남은 작업(전체메뉴 삭제·메뉴명 변경)에만 개발 리소스를 집중할 수 있도록 명확히 구분했다.
