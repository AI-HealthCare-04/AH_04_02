# 요구사항 정의서 수정 검토 기록 (v7 → v8)

이 문서는 `요구사항_정의서_v7.xlsx`에서 `요구사항_정의서_v8.xlsx`로 변경하며 반영한 구조 개편을 기록한 변경 이력이다. 배경은 2026-07-08 멘토링(`멘토링_대화내역_보고서_20260708.docx`)에서 확정받은 "사용자 요구사항 정의서는 클라이언트 그룹별로 작성하고, 그룹은 복약관리대상자·보호자·지원인력으로 한다"는 지침이며, 같은 라운드에서 이미 작성한 `API명세서_v7`·`ERD_v8`의 구현 여부 판정을 그대로 이어받아 정합성을 맞춘다.

## 배경 및 목적

- v7까지는 REQ-001~049(+백로그 1건)가 그룹 구분 없이 단일 시트에 나열돼 있었다. 실제로는 같은 REQ라도 복약관리대상자·보호자·지원인력이 각자 다른 목적으로 관여하는 경우가 많아(예: REQ-008 처방전 업로드 — 본인 업로드 vs 대리 업로드), 단일 문장으로는 "이 기능이 누구를 위한 것인지"가 흐려졌다.
- 멘토링 지침에 따라 이번 개정은 REQ를 재번호하거나 삭제하지 않고, 클라이언트 그룹별 시트로 재배치하면서 각 그룹 시점의 User Story(`~로서, ~하고 싶다. 그래야 ~`)를 새로 작성했다.
- 동시에 REQ별 "구현여부" 컬럼을 신설해 `API명세서_v7`·`ERD_v8`의 요구사항 추적표 판정과 동일한 기준(실제 `backend/models.py`·`routers/*.py` 실사)으로 채웠다.

## 1. 시트 구조를 클라이언트 그룹별로 재편 — 반영 완료

**결정**: 단일 `요구사항정의서` 시트를 없애고 `공통`/`복약관리대상자`/`보호자`/`지원인력` 4개 시트로 나눴다. 여러 그룹이 관여하는 REQ는 그룹마다 별도 행으로 중복 배치하되(같은 ID, 다른 User Story), 다음 기준으로 배정했다.

- **공통**: 3개 그룹 모두에 동일하게 적용되거나(예: REQ-001 회원가입·로그인), 특정 역할로 좁히기보다 시스템 규칙으로 서술하는 것이 더 정확한 항목(비기능 요구사항 대부분: REQ-028~032, 034, 039 등).
- **복약관리대상자**: 복약 당사자가 주 행위자인 항목(가이드 열람, 초대 발신, 생활습관 안내 등).
- **보호자** / **지원인력**: `caregivers.relation_type`(guardian vs caregiver/life_support_worker/social_worker/organization)에 대응해 분리했다. 초대 수락, 상태 입력, 모니터링, 대리 업로드처럼 두 그룹이 동일하게 관여하는 항목은 두 시트 모두에 각자의 표현으로 넣었다.
- 교육관리(REQ-040~044)는 실제 교육 수행 주체가 요양보호사·생활지원사·사회복지사이므로 전량 **지원인력**에만 배정했다(복약관리대상자는 교육의 대상이지 요청 주체가 아니므로 User Story 관점에서는 제외).

## 2. REQ별 "구현여부" 컬럼 신설 — 반영 완료

**결정**: 완료/부분/미구현/확인필요 4단계로 표기하고, `API명세서_v7`·`ERD_v8`과 동일한 실사 결과를 재사용했다. 다만 이번 그룹별 재구성 과정에서 기존 판정 중 2건의 오차를 발견해 정정했다.

- **REQ-045(회원가입 인적사항 확장)**: `ERD_v8` 요구사항 추적표에는 "완료"로 적었으나, `backend/models.py`를 다시 대조한 결과 `birth_date`만 실제 구현돼 있고 `address`(주소)는 `Patient`/`Caregiver` 어디에도 없으며, `special_notes`(특이사항)는 `Patient.note` 하나로만 부분 대응할 뿐 `Caregiver`에는 없다. **"완료" → "부분"으로 정정**했다.
- **REQ-048(저신뢰 확인 후 챗봇 연결 안내)**: 기존에는 "챗봇 컨텍스트로 자연스럽게 처리되니 완료"로 느슨하게 판단했으나, REQ-048이 실제로 요구하는 것은 "가이드 존재 여부에 따른 조건부 버튼 노출·안내 문구 분기"라는 구체적 UI 로직이다. 챗봇 자체는 `guide_result_id` 없이도 `patient_id` 기준으로 항상 열려 있어 이 분기 로직이 별도로 존재하지 않는다. **"완료" → "미구현"으로 정정**(프론트 실측 필요).

이 두 건은 `ERD_v8`을 다시 수정하지는 않고(범위 분리 원칙), 이 문서와 다음 ERD 개정 시 반영하도록 비고에 남겼다.

## 3. User Story 형식 도입 — 반영 완료

**결정**: 멘토링에서 요청받은 `As a [사용자], I want [기능], so that [목적]` 형식을 국문 `~로서, ~하고 싶다. 그래야 ~` 문형으로 통일해 전 REQ에 적용했다. 목적(so that) 문구는 v7의 상세내용·비고에서 실제 동기를 추출해 작성했고, 근거 없이 지어내지 않았다(예: REQ-004는 "제3자 도움이 필요한 대상자가 보호 공백 없이 관계를 정리"라는 목적을 상세내용의 care_level 분기 취지에서 그대로 가져옴).

## 4. 참고 시트(프로젝트의 목적/용어집/핵심 흐름) — 변경 없이 이관

**결정**: 이 3개 시트는 그룹 재구성과 무관해 v7 내용을 그대로 복사했다. 다음 개정에서 그룹별 시트 구조를 반영해 갱신이 필요하면 별도로 논의한다.

## 5. Figma 목업 대조는 이번 버전에서 보류

**발견**: 사용자가 회원가입 화면 Figma 목업(제작 중, 전체 프로젝트 80% 완성)과 REQ-045/046의 회원가입 인적사항 항목을 대조해달라고 요청했으나, 공유된 Figma Make 링크는 인증 기반 SPA라 자동 조회로 실제 화면 내용을 읽을 수 없었고 사용자도 현재 화면을 확인해줄 수 없는 상태였다.

**결정**: 이번 v8은 `backend/models.py` 실제 스키마만을 기준으로 작성하고, Figma 대조는 스크린샷이나 접근 가능한 링크가 제공되는 대로 별도 후속 작업으로 진행한다(메모리에 보류 상태로 기록).

## 6. (후속 수정) Figma 대조 완료 + 백로그 오류 발견·REQ-050 승격

**Figma 대조 완료(5절 "보류" 해소)**: 사용자가 회원가입 화면 스크린샷(Downloads)과, 이후 실제 프론트 소스 `frontend/src/pages/SignUp.tsx`(origin/dev 커밋 `06d057e`)를 직접 확인할 수 있게 해줘서 5절의 보류 상태를 해소했다. 확인 결과 개인 가입 화면엔 주소·특이사항 입력란이 정말 없고(REQ-045 "부분" 판정 재확인), `org_type` 드롭다운은 5개 값(요양원/정부기관/협회/보건소/기타)으로 제한된다. `ERD_v8.md`에 "Figma 회원가입 UI 대조" 절로 반영했다.

**백로그 오류 발견(사용자 지적)**: 사용자가 "요구사항정의서 revision_log에 개인/단체 회원가입 구분은 설계 미확정이라고 되어있는데 사실과 다르다"고 지적했다. 서브에이전트 1라운드 감사 → 2라운드 독립 재검증으로 확인한 결과:

- 이 "보류" 문구의 최초 등장 위치는 `v5_to_v6_revision_log.md`가 아니라 **`v6_to_v7_revision_log.md` 9행·43~46행·70행**이었다(v5_to_v6엔 이 주제 언급 자체가 없음 — 이번에 위치를 다시 확인해 정정).
- `backend/models.py:94,101~108`(`relation_type=organization`, `org_name`/`org_type`/`business_reg_no`/`manager_name`/`manager_phone`)과 `monitoring_router.py:160~208`(`CaregiverCreate`/`CaregiverPublic`/`create_caregiver`)에 이 기능이 이미 완전히 구현돼 있고, `frontend/src/pages/SignUp.tsx`에도 기관 가입 UI가 실제로 존재한다. **"설계 미확정"은 더 이상 사실이 아니다.**
- 더 심각한 문제로, `요구사항_정의서_v8.xlsx`는 자체 모순을 안고 있었다 — '지원인력' 시트 헤더가 이미 `relation_type=caregiver/life_support_worker/social_worker/organization`을 기정 값으로 서술하면서도, '백로그' 시트는 같은 파일 안에서 "설계 미확정"이라는 구버전 문구를 그대로 방치하고 있었다.

**결정**: 백로그 시트에서 해당 행(개인/단체 회원가입 구분)을 삭제하고, **REQ-050**(사용자관리, 지원인력 시트, 구현여부=완료)으로 정식 승격했다. 같은 재검토 과정에서 REQ-030(공통)의 구현 판단 근거가 "최소권한 접근"(인수조건에 명시된 항목)을 다루지 않고 있어 `records_router.py`/`ocr_router.py`/`rag_router.py`/`chat_router.py`에 인증 Depends가 0건이라는 사실을 추가했고, REQ-045의 근거가 언급하던 "GET /users/me"가 실재하지 않는 경로임을 확인해 실제로는 `GET /monitoring/patients`·`GET /monitoring/caregivers`가 그 역할을 한다고 정정했다. `API명세서_v7`·`ERD_v8`에서도 같은 재검토 라운드로 발견한 오류들을 각 문서의 revision log에 별도로 기록했다(`API명세서_v6_to_v7_revision_log.md` 6절, `ERD_v7_to_v8_revision_log.md` 5절).

## 팀에 설명할 핵심 결정

1. **REQ 번호는 그대로 유지하고 시트만 그룹별로 나눴다** — REQ-001~049 번호 체계를 다음 버전에서도 그대로 추적할 수 있게, 재번호하지 않고 그룹 시트 간 중복 배치로 해결했다.
2. **같은 REQ가 여러 시트에 나타나는 것은 중복이 아니라 관점 차이다** — 예: REQ-008(처방전 업로드)은 복약관리대상자·보호자·지원인력 시트 모두에 있지만 각각 "본인 업로드"/"대리 업로드(보호자)"/"대리 업로드(지원인력)"로 다른 User Story를 담고 있다.
3. **구현여부 판정에서 REQ-045·REQ-048 2건을 "완료"에서 하향 정정했다** — 이전 문서(ERD_v8)의 느슨한 판정을 그룹별로 다시 짚어보는 과정에서 발견했다. ERD_v8 자체는 이번에 수정하지 않았으니, 다음 ERD 개정 시 함께 정정이 필요하다.
4. **Figma 회원가입 화면 대조는 이후 완료했다** — 스크린샷과 실제 프론트 소스(`SignUp.tsx`)로 확인, REQ-045 판정을 재확인하고 ERD_v8에 반영했다.
5. **"개인/단체 회원가입 구분"은 백로그가 아니라 REQ-050(완료)이다** — 사용자 지적으로 발견, 서브에이전트 2라운드 교차검증으로 확인. 문서에 남아있던 사실관계 오류는 발견 즉시 정정해야 하며, "언젠가 다음 버전에서" 미루지 않는다.
6. **이전 버전 파일(`요구사항_정의서_v7.xlsx`)은 수정하지 않고 보존, 이번 개정은 새 버전 파일로 버전업한다.**
