## DEV-01. 실제 CLOVA OCR 인증키가 커밋 대상 템플릿 파일에 노출 — CRITICAL

**무엇이 발생했는가**: git 추적 대상인 `backend/.env.example`에 실제 `CLOVA_OCR_API_URL`/
`CLOVA_OCR_SECRET_KEY` 값이 (아직 커밋되진 않았지만) 작업트리에 채워져 있는 상태로 발견됨.

**원인**: 실제 키를 테스트하려고 `.env`가 아니라 템플릿 파일(`.env.example`)에 직접 채워
넣음 — 두 파일의 역할(예시 vs 실제 비밀값) 구분 없이 작업.

**시정조치** — ✅ 실행됨: 두 값을 즉시 빈 값으로 되돌리고 `git diff`로 커밋 이력과 동일함을
확인. 실제 값은 gitignore 대상인 `backend/.env`로 이전.

**예방조치** — ⬜ 앞으로 해결해야 함: 비밀값이 들어갈 수 있는 파일(`.env.example` 등)을
편집하기 전 "이게 커밋 대상인가"를 확인하는 절차를 팀 문서에 명문화할 것. → `docs/etc/team-rules.md`
§11에 반영(이 커밋에 포함).

## DEV-02. PR #46 — production 환경 SSL 가드 우회 경로 존재 — HIGH

**무엇이 발생했는가**: `APP_ENV=production`인데 `DATABASE_SSL_REQUIRED` 자체를 설정하지
않으면 SSL 검증 가드를 완전히 건너뛰고 평문 연결이 그대로 생성됨(사용자가 직접 재현해 보고).

**원인**: 가드 로직이 `elif DATABASE_SSL_REQUIRED:` 분기 안에만 있어서, 그 분기 자체에
안 들어가는 경로(변수 미설정)를 놓침 — "값이 잘못된 경우"만 막고 "아예 안 켠 경우"는 안 막음.

**시정조치** — ✅ 실행됨: 가드를 분기 진입 전으로 이동해 `APP_ENV=production`이면
`DATABASE_SSL_REQUIRED` 값과 무관하게 항상 먼저 검사하도록 재작성. PR #46 병합 완료.

**예방조치** — ✅ 실행됨: 회귀 테스트 3건(가드 통과/차단 각 조합)을 `test_database_env.py`에
실제로 추가해 병합 — 같은 종류의 "분기 밖 우회"가 재발하면 테스트로 즉시 검출된다.

## DEV-03. PR #48 — 비밀번호 재설정/탈퇴/잠금 보안 결함 4건 — CRITICAL + HIGH×2 + MEDIUM

**무엇이 발생했는가**: 1차 구현본에 팀원 리뷰로 4건 발견 —
1. 재설정 코드 무제한 누적/브루트포스 (CRITICAL)
2. 탈퇴 후 기존 access/refresh 토큰 미무효화 (HIGH)
3. 계정 잠금 영구화 — 비인증 DoS + 복구불가 (HIGH)
4. `purge_expired_accounts.py` 기본 동작이 파괴적 (MEDIUM)

**원인**: 각 기능을 "정상 시나리오" 위주로 구현하고, 공격자 관점(반복 요청, 기존 세션 재사용,
잠금 지속시간)의 악용 경로를 1차 구현 단계에서 충분히 검토하지 않음.

**시정조치** — ✅ 실행됨: 4건 모두 수정(코드 재발급 시 이전 코드 무효화 + 계정당 요청 횟수
제한 + verify 시도 횟수 제한, `deactivated_at` 전 구간 체크, 30분 자동 잠금해제, 스크립트
안전 기본값 반전) 후 security-reviewer 서브에이전트로 2라운드 독립 검증 — 1라운드에서
"쿨다운 우회로 요청 횟수 제한 무력화" 가능성을 자체 발견해 즉시 반영, 2라운드에서 최종
확인. PR #48 병합 완료.

**예방조치** — ✅ 실행됨: 인증/계정 상태 변경 엔드포인트용 악용 경로 점검 체크리스트를
`docs/etc/security-checklist.md`로 실제 작성(이 커밋에 포함) — 다음 유사 기능부터 바로 참고 가능.

## DEV-04. PR #47 — Alembic downgrade 인덱스 재생성 누락 — HIGH

**무엇이 발생했는가**: `downgrade()`가 `token` 컬럼을 되돌리면서 원래 있던
`ix_invitations_token` 유니크 인덱스는 복원하지 않아, `downgrade` 후 재`upgrade`가
"No such index" 에러로 실패.

**원인**: 마이그레이션 작성 시 `upgrade()`/`downgrade()`를 완전한 대칭으로 검증하지 않고
forward 방향만 테스트함.

**시정조치** — ✅ 실행됨: 리뷰에서 재현 후 팀원이 `downgrade()` 끝에 인덱스 재생성 추가
(커밋 `825c417`), 재검증 통과.

**예방조치** — ✅ 실행됨: `upgrade → downgrade → upgrade` 왕복 테스트를 신규 마이그레이션
작성 시 필수 절차로 `docs/etc/team-rules.md`에 명문화(이 커밋에 포함).

## DEV-05. Alembic 리비전 두 개의 head — PR #47/#48 동시 브랜치 충돌 — HIGH (배포 프로세스)

**무엇이 발생했는가**: PR #47(`d9616a377d8c`)과 PR #48(`38a30cdfa517`)이 같은 부모
리비전(`bcdbae97c089`)에서 각자 새 마이그레이션을 브랜치 — 둘 다 머지되면 Alembic이
head 2개로 인식해 `upgrade head`가 막히는 상태였음.

**원인**: 두 작업이 병렬로 진행되며 서로의 마이그레이션 존재를 미리 확인하지 않음 — 마이그레이션을
새로 만들 때 "지금 다른 브랜치에도 진행 중인 마이그레이션이 있는지" 확인 절차가 없었음.

**시정조치** — ✅ 실행됨: PR #47이 먼저 머지된 뒤, PR #48의 `down_revision`을
`d9616a377d8c`로 재배치(리비전이 실 DB 어디에도 적용된 적 없어 안전하게 재배치 가능했음) —
전체 체인 up/down 재검증 후 병합, 단일 선형 체인 확인됨.

**예방조치** — ✅ 실행됨: "공용 DB에 여러 명이 동시에 마이그레이션 작업 중일 때 머지 순서를
먼저 정하고 나중 순번이 리베이스한다"는 규칙을 `docs/etc/team-rules.md`에 명문화(이 커밋에 포함).

## DEV-06. 로컬 메인 디렉토리 코드가 실 DB 스키마보다 뒤처져 초대 기능 장애 — HIGH (현재 진행형)

**무엇이 발생했는가**: PR #47 마이그레이션을 검증차 실제 Aiven DB에 먼저 적용했는데, 로컬에서
실행 중인 서버(메인 프로젝트 디렉토리)는 그 코드를 pull하지 않은 채(10+커밋 뒤처짐) 계속
실행 중이었음 — DB는 새 스키마, 서버 코드는 옛 스키마를 기대해 초대 기능에서
`Unknown column 'invited_phone'` 오류 발생.

**원인**: 공유 DB에 마이그레이션을 적용하는 작업과, 그 DB를 바라보는 로컬 실행 환경의 코드를
동기화하는 작업을 같은 순서로 묶어서 처리하지 않음 — "DB를 먼저 바꾸고 코드는 나중에"가
실행 중인 로컬 서버 기준으로는 즉시 불일치를 만든다는 점을 반영하지 않음.

**시정조치** — 🟣 보류(의도적 미해결): 사용자 확인 하에 고치지 않기로 결정 — 로컬 `dev`
브랜치도, DB 스키마도 현재 상태 그대로 유지(초대 기능을 지금 당장 쓰지 않음). "해결"이
아니라 "지금은 안 건드리기"를 선택한 것 — 초대 기능은 이 로컬 서버에서 여전히 깨져 있다.

**예방조치** — ✅ 실행됨: 공유 DB에 스키마 변경을 적용하기 전 로컬 실행 환경 동기화 여부를
먼저 확인하는 절차를 `docs/etc/shared-dev-db-setup.md`에 신규 섹션으로 작성(이 커밋에 포함).
