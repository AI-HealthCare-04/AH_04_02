# 요구사항 정의서 수정 검토 기록

이 문서는 `요구사항_정의서_v3.xlsx`에 반영한 요구사항 수정사항과 3번 시트 변경추적성 내용을 분리해 기록한 변경 이력이다.

## 1번 시트 수정안

### REQ-001 사용자 인증 보완

로그인 성공 시 단기 access token과 장기 refresh token을 발급하고, 사용자는 유효한 refresh token으로 재로그인 없이 access token을 갱신할 수 있어야 한다. 갱신 성공 시 refresh token을 순환 발급하고 기존 토큰을 폐기해야 한다.

### REQ-002 신뢰관계 초대 보완

복약관리 대상자는 가입 여부와 관계없이 전화번호로 보호자·지원인력을 초대할 수 있어야 한다. 시스템은 만료시각이 있는 일회성 초대 토큰을 발급하고 원문이 아닌 해시를 저장해야 한다. 미가입 수신자는 해당 전화번호를 인증해 가입·로그인한 후 초대를 수락할 수 있어야 한다.

### REQ-003 초대 수락·거절 보완

초대 수신자는 만료 전 초대를 수락하거나 거절할 수 있어야 한다. 수락 시 인증된 전화번호 일치 여부를 확인하고 승인된 신뢰관계를 생성하며 승인자·승인시각을 저장해야 한다. 만료·사용 완료·수신자 불일치 토큰은 사용할 수 없어야 한다.

### REQ-004 연결 해제 반려 규칙 보완

`third_party_needed` 상태의 연결 해제 요청은 승인 또는 반려할 수 있어야 한다. 승인 시 관계를 `revoked`로 변경하고, 반려 시 해제 요청을 종료한 뒤 관계를 `approved`로 복귀시켜야 한다. 결정자·결정시각·결과를 저장해야 한다.

### REQ-007a 조사 수정 및 표시 기준

`승인된 보호자·지원인력가 없으면`을 `승인된 보호자·지원인력이 없으면`으로 수정한다. 권유 안내 비표시는 평가 단건이 아니라 복약관리 대상자 기준으로 30일 동안 유지하며 새 평가 생성만으로 초기화하지 않는다.

### REQ-007 안전 알림 대상 보완

`third_party_needed`에서는 알림 수신에 동의한 승인 보호자·지원인력에게 발송한다. 최소 한 명의 수신 가능 관계자 유지를 권고하지만 모든 사용자의 설정 선택권을 보장한다.

### REQ-011 OCR 확인 상태 보완

저신뢰도 OCR 결과는 요청 검증 실패가 아니라 `review_required` 처리 상태로 분류해야 한다. 사용자가 결과를 확인·수정하기 전 가이드를 확정하지 않아야 하며 일반 입력 검증 실패와 구분되는 오류 코드를 제공해야 한다.

### REQ-020 캐시 무효화 보완

시스템은 진단명·약물 조합과 출처 데이터 버전을 포함한 캐시 키를 관리해야 한다. 캐시 유효기간이 지나거나 출처 버전이 변경되면 기존 가이드를 캐시 적중으로 사용하지 않고 새 가이드를 생성해야 한다.

### REQ-026c 알림 우선순위 보완

복약관리 대상자·보호자·지원인력은 각자 알림 설정을 자유롭게 변경한다. 실제 발송에는 일정별 설정과 수신자의 돌봄·전체 푸시 설정을 모두 반영한다. `third_party_needed`에서 수신 가능한 관계자가 0명이면 최소 한 명 유지를 권고하되 설정을 강제로 켜거나 변경 요청을 거절하지 않는다. 승인 관계 자체가 0명이면 REQ-007a를 적용한다.

### REQ-035 탈퇴 생명주기 보완

시스템은 탈퇴 요청시각, 계정 비활성화 시각, 개인정보 영구 삭제 예정시각을 관리해야 한다. 실제 영구 삭제 완료 증빙은 개인정보가 제거된 감사 기록으로 보존해야 한다.

### REQ-039 로그인 5회 실패 복구

로그인 5회 연속 실패 시 가입 당시 인증된 이메일 또는 연락처로 일회용 임시번호를 자동 전송한다. 임시번호 인증 후에는 비밀번호 재설정 전용 세션만 허용하고 새 비밀번호 설정 완료 후 계정 잠금과 실패 횟수를 초기화한다.

### REQ-044 재교육 회차 보완

교육이 완료된 뒤 장기간 미사용, 인지·건강 상태 변화 또는 사용자 요청으로 재교육이 필요하면 새 교육 회차를 시작할 수 있어야 한다. 각 회차의 시작일, 종료일, 단계, 담당 지원인력, 지원 이력을 보존해야 하며 대상자별 현재 교육 회차는 최대 1개만 존재해야 한다. 일시중지는 현재 회차를 유지하고 완료된 회차는 수정하지 않아야 한다.

## 3번 시트 변경추적성 반영 내역

아래 표는 Excel 3번 시트에 별도 행으로 옮길 수 있는 내용이다.

| 검토항목 | 1번 시트 반영안 | 연계 문서 | 검증 상태 |
|---|---|---|---|
| 조사 오타 | REQ-007a의 `지원인력가`를 `지원인력이`로 수정 | API 섹션 3·7, ERD 핵심 규칙 | 반영 완료 |
| HTTP 상태 구분 | REQ-011 저신뢰 OCR을 `review_required` 작업 상태로 정의; `422`는 일반 검증 실패 전용 | API 상태 코드·OCR 상태 조회 | 반영 완료 |
| 토큰 갱신 | REQ-001에 refresh token을 이용한 access token 갱신·순환 발급 추가 | `POST /auth/refresh` | 반영 완료 |
| 초대 저장 구조 | REQ-002에 가입 전 전화번호 초대, 토큰 해시·만료 관리 추가 | `trust_invitations` | 반영 완료 |
| 초대 수락 검증 | REQ-003에 전화번호 일치, 승인자·승인시각 저장 추가 | 초대 accept/reject API, `trust_relations` | 반영 완료 |
| 해제 반려 | REQ-004에 승인 시 revoked, 반려 시 approved 복귀 규칙 추가 | revocation-approval API·결정 필드 | 반영 완료 |
| 알림 선택권 | REQ-026c에 모든 사용자의 설정 자유와 최소 한 명 유지 권고 추가 | `notification_settings`, `medication_schedules` | 반영 완료 |
| 권고 정보 계산 | `active_safety_recipient_count`, `should_recommend`를 계산 응답값으로 확정 | 알림 설정 API | 반영 완료 |
| 탈퇴 시각 | REQ-035에 요청·비활성화·삭제예정 시각 구분 | `users` 생명주기 필드 | 반영 완료 |
| 캐시 무효화 | REQ-020에 출처 버전 포함 캐시 키와 만료 기준 추가 | `guide_results.cache_key`, `cache_expires_at` | 반영 완료 |
| 권유 안내 기준 | REQ-007a를 대상자 단위 30일 비표시로 확정 | dismissal의 `assessment_id` 제거 | 반영 완료 |
| 재교육 회차 | REQ-044에 재교육 시작과 과거 회차 보존 추가 | `education_profiles` 1:N 회차 구조 | 반영 완료 |
| 영구 삭제 완료 감사 | REQ-035의 실제 삭제 완료를 비식별 감사기록으로 보존 | `privacy_purge_audits` | 반영 완료 |
| 도움 단계 알림 추적 | REQ-007을 동의한 관계자에게 발송하고 최소 한 명 유지는 권고로 확정 | `notifications`, `notification_deliveries` | 반영 완료 |
| 의료자문 고지 추적 | REQ-032의 가이드·챗봇 고지 연결 | `guide_results.disclaimer` | 반영 완료 |
| 계정 잠금·복구 | REQ-039의 임시번호 자동 전송·임시 로그인·강제 비밀번호 재설정 | `auth_temporary_codes`, temporary-login API | 반영 완료 |

## 팀에 설명할 핵심 결정

1. 안전 알림 권고 정보는 서버가 대상자별로 계산해 반환하므로 중복 DB 컬럼을 만들지 않는다.
2. 초대와 실제 관계를 분리하면 미가입 사용자와 만료 토큰을 자연스럽게 처리할 수 있다.
3. 해제 반려는 관계 자체의 거절이 아니므로 `rejected`가 아니라 `approved` 복귀가 맞다.
4. 재교육을 허용하면 대상자당 프로필 하나라는 UK를 제거하고 회차별 이력을 보존해야 한다.
5. `users.deleted_at` 하나보다 탈퇴 요청·비활성화·삭제 예정 시각을 분리하는 것이 정책을 정확히 표현한다.
