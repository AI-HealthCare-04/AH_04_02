# 요구사항 정의서 수정 검토 기록 (v6 → v7)

이 문서는 `요구사항_정의서_v6.xlsx`에서 `요구사항_정의서_v7.xlsx`로 변경하며 반영한 회원가입 개편 관련 신규 요구사항을 기록한 변경 이력이다. 배경은 `docs/draft_signup_mentoring_feedback_v1.md`이며, 같은 라운드에서 이미 반영한 `docs/ERD/revision_log/ERD_v6_to_v7_revision_log.md`·`docs/API명세서/revision_log/API명세서_v5_to_v6_revision_log.md`의 결정을 요구사항 정의서에 일치시킨다.

## 배경 및 목적

- 멘토링 피드백(2026-07-03)으로 회원가입 인적사항·보호자 연결·OCR 저신뢰 확인 후 처리·앱 최초 진입 화면에 대한 결정이 확정되었다.
- 이번 개정은 그 확정 결정을 ERD v7 / API 명세서 v6와 동일한 내용으로 요구사항 정의서에 신규 REQ로 추가하는 작업이다. 기존 REQ-001~044 행은 수정·재번호하지 않았다.
- "개인/단체 회원가입 구분"은 설계 미확정이라 정식 REQ를 부여하지 않고 백로그 항목으로만 남겼다.

## 변경 항목 (신규 REQ)

기존 최대 번호 REQ-044 다음으로 REQ-045~REQ-049를 추가하고, 백로그 행 1건을 추가했다.

### REQ-045 회원가입 인적사항 확장(생년월일·주소·특이사항) — `사용자관리`

- 회원가입 시 이름·비밀번호·이메일/전화번호 외에 `birthday`(생년월일)·`address`(주소)·`special_notes`(특이사항)를 선택 입력받아 `users`에 저장하고 `GET /users/me` 응답에 노출한다.
- 주민등록번호는 개인정보보호법상 고유식별정보 수집 제한과 개인정보 최소화 원칙에 따라 수집하지 않고, 본인확인 목적은 생년월일로 대체한다.
- 비고에 "'아이디' 별도 필드 미신설(이메일/전화번호 로그인 유지)"을 명시했다.

### REQ-046 가입 시 보호자 연락처 자동 초대 — `돌봄관리`

- 가입 시 `guardian_phone`(보호자·지원인력 연락처)을 입력하면 서버가 기존 돌봄관계 초대(`care_relation_invitations`)와 동일한 로직으로 초대를 자동 생성하고 응답에 `invitation_id`를 포함한다.
- 새 컬럼·테이블을 만들지 않고 전화번호 기반 초대 하나로 "연결되는 ID"와 "보호자 연락처"를 통합한다.
- 승인은 기존 초대 수락 절차(REQ-003)를 그대로 따르며 가입 즉시 돌봄관계가 생성되지는 않는다.

### REQ-047 저신뢰 확인 시 약물명 오타 제안 — `예외처리`

- `review_required` 항목을 `PATCH /medical-records/{record_id}/medications/{medication_id}`로 확인·수정할 때 입력한 약물명이 약물명 사전과 정확히 일치하지 않으면 가장 유사한 후보를 `typo_suggestion`으로 응답에 포함한다.
- `typo_suggestion`은 저장하지 않는 응답 전용 값이다. REQ-011 저신뢰 확인 흐름의 확장이다.

### REQ-048 저신뢰 확인 후 챗봇 연결 안내 — `챗봇`

- 확인 후에도 문제가 있으면, 해당 기록의 가이드가 이미 생성된 경우 그 `guide_result_id`로 챗봇(REQ-021, `/chat`)에 진입하는 버튼을 노출한다.
- 가이드가 아직 없으면 챗봇을 열지 않고 "가이드가 생성되면 챗봇으로 질문할 수 있다"는 안내 문구만 표시한다.
- `/chat` 요청 스키마는 확장하지 않고 기존 `guide_result_id` 기반을 그대로 사용하는 UI 규칙이다.

### REQ-049 앱 최초 실행 화면 정책 — `사용자관리`

- 앱 최초 실행 시 유효한 `refresh_token`이 있으면 자동 로그인 후 홈 화면, 없거나 만료되었으면 회원가입 화면을 기본으로 표시하되 "이미 계정이 있으신가요? 로그인" 링크로 로그인 화면에 진입할 수 있다.
- 별도 API 없이 클라이언트 동작 규약으로 정의한다. REQ-001과 연계된다.

### 백로그: 개인/단체 회원가입 구분(보류)

- "단체"의 정의·로그인 단위·추가 서류(사업자등록번호 등) 등 설계 결정이 미확정이라 이번 버전 범위에서 제외했다.
- 정식 REQ 번호를 부여하지 않고 `ID=(백로그)`, `구분=백로그`의 별도 행으로 남겼다. 설계 확정(`account_type`/`organizations`) 후 정식 요구사항으로 승격한다.

## 시트별 반영

- **`요구사항정의서` 시트**: 기존 컬럼 순서(`ID, 구분, 카테고리, 요구사항명칭, 상세내용, 인수조건, 생활습관 개선 가이드/예시, 우선순위, 비고, 우선순위_재평가_근거`)를 그대로 유지하며 REQ-045~049 + 백로그 1행을 append했다. 우선순위는 모두 Medium(부가·개편 성격), 인수조건은 각 상세내용에서만 도출했다.
- **`용어집` 시트**: `typo_suggestion (오타 제안)`, `guardian_phone (보호자 연락처 자동초대)`, `특이사항 (special_notes)` 3개 용어를 추가했다.
- **`핵심 흐름` 시트**: (1) 기존 "처방전 업로드 → OCR → 가이드 생성 → 챗봇 질문" 흐름에 4a(오타 제안)·4b(챗봇 연결 안내) 단계를 추가했고, (2) "회원가입 인적사항 입력 → 보호자 연락처 자동초대 → 수락" 흐름 1건을 신설했다.
- 서식은 v6과 동일하게 유지했다(헤더 굵게·음영 `FFD9E1F2`·freeze A2, 장문 셀 `wrap_text`, 기존 컬럼 폭). 신규 셀에도 `wrap_text=True`, `vertical=top`을 적용했다.

## 시트/행 수 변경 요약

| 항목 | v6 | v7 |
|---|---|---|
| 시트 수 | 4 | 4 (변동 없음) |
| 요구사항정의서 행 수(헤더 포함) | 48 | 54 (+REQ-045~049, +백로그 1행) |
| 용어집 행 수(헤더 포함) | 16 | 19 (+3 용어) |
| 핵심 흐름 행 수(헤더 포함) | 5 | 6 (+회원가입 흐름 1건, OCR 흐름 확장) |

## 팀에 설명할 핵심 결정

1. **주민번호는 채택하지 않는다.** 개인정보보호법상 고유식별정보 수집 제한과 현재 설계의 개인정보 최소화 원칙(복구 불가능한 해시만 보존)에 정면으로 어긋나기 때문이다. 본인확인 목적은 `birthday`(생년월일)로 대체했다(REQ-045).
2. **"아이디" 별도 필드를 신설하지 않는다.** 기존 이메일/전화번호 로그인을 유지한다. 별도 로그인 식별자를 만들지 않기로 한 결정이다.
3. **"연결되는 ID"·"보호자 연락처"는 하나로 통합한다.** 아이디 개념 자체가 없으므로 "기존 계정 ID 직접 입력" 방식은 자연스럽지 않다. 두 요청을 `guardian_phone` 전화번호 기반 자동 초대(기존 `care_relation_invitations` 재사용) 하나로 흡수했다 — 신규 스키마 없음(REQ-046).
4. **챗봇 연결은 스키마를 확장하지 않는다.** 저신뢰 확인 후 대부분의 경우 가이드가 이미 존재하므로, 기존 `guide_result_id` 기반 `/chat`을 그대로 쓰고 가이드 존재 시에만 진입 버튼을 노출하는 UI 규칙만 추가했다. 불필요한 스키마 확장을 피했다(REQ-048).
5. **개인/단체 구분은 보류한다.** 단체의 정의·로그인 단위·추가 서류 등 설계 결정이 많아 이번 스프린트에서 확정하지 않고 백로그로만 남겼다. 정식 REQ 번호는 부여하지 않았다.
6. 이번 버전도 문서(요구사항 정의서·ERD·API 명세서) 변경만 반영하며, 실제 FastAPI 코드는 아직 문서와 어긋난 상태라 별도 코드 정합화 작업이 선행되어야 한다.
7. `요구사항_정의서_v6.xlsx`는 수정하지 않고 보존했으며, 본 개정은 `요구사항_정의서_v7.xlsx`로 버전업했다.
