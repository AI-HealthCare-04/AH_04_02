# 보안 체크리스트 — 인증/계정 상태 변경 기능

로그인, 비밀번호 재설정, 회원 탈퇴, 계정 잠금처럼 **계정 상태를 바꾸거나 인증 자체를
다루는 엔드포인트**를 새로 만들 때 구현 직후(코드 리뷰 전) 스스로 점검하는 목록이다.

PR #48(REQ-039 로그인 잠금·비밀번호 재설정, REQ-035 회원 탈퇴)의 1차 구현본이 "정상
시나리오" 위주로만 짜여서, 팀원 리뷰에서 CRITICAL 1건 + HIGH 2건 + MEDIUM 1건이 한꺼번에
나온 적이 있다(`docs/deviation_log/deviation-log-2026-07-16.md` DEV-03 참고) — 이 체크리스트는 그 4건이
공통으로 놓쳤던 관점을 다음에 반복하지 않기 위한 것이다.

## 1. 반복 요청 (Rate limiting)

- [ ] 이 엔드포인트를 **인증 없이** 무제한 반복 호출할 수 있는가? 가능하다면 계정당/IP당
      요청 횟수 제한이 있는가?
- [ ] "쿨다운"만으로 막았다면, 그 쿨다운이 **상태를 인위적으로 리셋시키는 다른 액션**으로
      우회되지 않는가? (예: 코드를 일부러 틀려서 무효화 → 쿨다운 해제 → 재요청 반복)
- [ ] 재요청 시 이전에 발급한 토큰/코드가 **자동으로 무효화**되는가, 아니면 계속 쌓이는가?
      쌓인다면 브루트포스 성공 확률이 요청 횟수에 비례해 올라간다.

## 2. 시도 횟수 (Brute-force)

- [ ] 사용자가 직접 입력하는 코드/비밀번호를 검증하는 곳이라면, 시도 횟수 제한이 있는가?
- [ ] 제한을 넘기면 어떻게 되는가 — 그 코드/세션이 완전히 무효화되는가, 아니면 계속 시도
      가능한가?

## 3. 계정 상태 전환의 파급 범위

- [ ] 계정을 잠그거나(`locked_at`), 비활성화하거나(`deactivated_at`), 비밀번호를 바꾸는
      액션이 있다면 — **이미 발급된 access_token/refresh_token도 그 즉시 무효화되는가?**
      (`get_current_actor` 계열 의존성과 토큰 재발급 엔드포인트 양쪽 다 확인)
- [ ] 로그인 시점에만 상태를 확인하고, 그 이후 매 요청에서는 재확인하지 않는 구조는 아닌가?

## 4. 잠금/차단의 지속 시간

- [ ] 계정 잠금·차단이 **영구적**이라면: (a) 본인 확인 수단(이메일 등)이 없는 사용자는
      영영 복구가 안 되는가? (b) identifier만 아는 제3자가 비인증 상태로 타인 계정을
      임의로 잠글 수 있는(DoS) 구조는 아닌가? 둘 중 하나라도 해당하면 자동 만료(TTL)를
      검토한다.

## 5. 파괴적 동작의 기본값

- [ ] 실제 데이터를 삭제/변경하는 스크립트라면, **플래그 없이 실행했을 때 기본 동작이
      안전한가(dry-run 또는 거부)**? `migrate_local_data.py`의 `--yes-i-have-a-backup`
      관례를 따를 것 — 실행을 거부하는 게 기본값이어야 한다.

## 6. 정보 노출

- [ ] 실패 사유(계정 없음 vs 비밀번호 틀림 vs 잠김)를 응답에서 구분해서 알려주고 있지
      않은가? 클라이언트에는 통합된 일반 메시지만 주고, 구분은 서버 로그에만 남긴다.
