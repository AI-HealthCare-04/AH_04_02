# 팀 규칙

## 1. 근무 시간
- 10:00 ~ 18:40 프로젝트 시간 (쉬는시간 40분 제외)
- 55분 수업/작업 + 5분 휴식 패턴

## 2. 개발 환경
- PyCharm 통일

## 3. 주간 계획
- 매주 월요일 아침 10시, 한 주의 프로젝트 구성 계획

## 4. 일일 계획
- 매일 아침 10시, 그날 할 작업 계획

## 5. 소통 채널
- 공식 채널: 카카오톡(또는 디스코드) 단체방, 2시간 이내 응답 원칙
- 급한 이슈(빌드 깨짐, 작업 막힘 등)는 "급함" 표시 후 즉시 공유

## 6. Git / 코드 컨벤션
- 브랜치명: `feature/기능명_이름` (예: `feature/ocr-extraction_sh`)
- 커밋 메시지: `feat: OCR 연동`, `fix: 인증 에러 수정`, `docs: README 갱신` 형식
- PR은 팀원 1명 이상 리뷰·승인 후 merge (코드리뷰는 받은 지 24시간 이내 확인)
- merge 전 로컬에서 직접 실행 확인 후 push

## 7. 데일리 스크럼 / 멘토링
- 매일 10시(휴식 후) 15분 이내, 전일진행상황/금일예정/막힌점 공유
- 멘토링 사전보고서는 멘토링 전날까지 작성, 담당자 매주 순환

## 8. 이슈/막힘 공유
- 30분~1시간 이상 막히면 바로 공유 (혼자 끌고 가지 않기)
- 해결 어려운 이슈는 GitHub Issues에 등록해 기록 남기기

## 9. 지각/결석/일정변경
- 사전 공유는 최소 1시간 전 단체방에 (지각/조퇴/멘토링 불참 포함)

## 10. 의사결정
- 기술/설계 의견 충돌 시 30분 토론 → 미해결 시 팀장 최종 결정, 결정 이유는 짧게 문서화

## 11. 보안/환경
- API 키·비밀번호 커밋 금지 — `.env` + `.gitignore` 필수
- requirements.txt / pyproject.toml로 패키지 버전 고정
- 비밀값이 들어갈 수 있는 파일(`.env.example` 같은 템플릿 포함)을 편집하기 전, 항상
  "이 파일이 커밋 대상인가"부터 확인한다 — 템플릿 파일에 실제 키를 채워 테스트하지 않기
  (2026-07-16, `docs/deviation_log/deviation-log-2026-07-16.md` DEV-01)
- 인증/계정 상태 변경 기능(로그인, 비밀번호 재설정, 탈퇴, 계정 잠금 등)을 구현하면 코드
  리뷰 전에 `docs/etc/security-checklist.md`로 자체 점검한다 (2026-07-16, DEV-03)

## 12. Alembic 마이그레이션
- 신규 마이그레이션은 병합 전 반드시 `upgrade head → downgrade -1 → upgrade head` 왕복
  테스트를 거친다 — forward 방향만 확인하면 downgrade 쪽 비대칭 버그(인덱스 누락 등)를
  놓친다 (2026-07-16, DEV-04)
- 공용 개발 DB에 여러 명이 동시에 마이그레이션 작업 중이면, 새 리비전을 만들기 전에
  다른 브랜치에 진행 중인 마이그레이션이 있는지 먼저 확인한다. 같은 부모 리비전에서
  독립적으로 브랜치하면 두 PR이 모두 머지될 때 Alembic이 head 2개로 갈라진다 — 머지
  순서를 먼저 정하고, 나중에 머지되는 쪽이 `down_revision`을 재배치(리베이스)한다
  (2026-07-16, DEV-05)
- 공유 DB에 스키마 변경을 실제로 적용하기 전 로컬 실행 환경 동기화 여부를 확인하는
  절차는 `docs/etc/shared-dev-db-setup.md` 참고 (2026-07-16, DEV-06)

## 13. 환경변수 변경

- 배포는 `git pull + docker compose up -d --build`만 하고 `.env`는 절대 안 건드린다 —
  `CORS_ALLOWED_ORIGINS`/`VITE_MONITORING_API_URL` 같은 값이 바뀌면 EC2 서버의 `.env`도
  직접 갱신해야 한다. 체크리스트는 `docs/etc/env-var-checklist.md` 참고
  (2026-07-28, 도메인 변경 후 로그인 불가 사고)
