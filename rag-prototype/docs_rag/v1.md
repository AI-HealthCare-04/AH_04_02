## 1. "제품명(전체 품목명, ○○정500밀리그램 스타일)"이 들어가는 위치

역할별로 4그룹으로 나뉩니다. 실제로 팀원과 합의가 필요한 지점은 **③, ④번**이고, ①②는 식약처 API 원본 데이터를 그대로 다루는 부분이라 건드릴 여지가 없습니다.

### ① 원본 저장 (API가 내려준 값 그대로, 손댄 적 없음)

| 파일:라인 | 내용 |
|---|---|
| `rag_prototype/schemas.py:8` | `DrugInfo.item_name` (alias `itemName`) — API 응답 원본 |
| `rag_prototype/chunking.py:13, 19` | 벡터DB에 저장되는 `page_content`/`metadata["item_name"]`에 전체 품목명 그대로 박힘 |

### ② 정확매칭 기준 (완전히 같아야 걸림)

| 파일:라인 | 내용 |
|---|---|
| `rag_prototype/vectorstore.py:32, 35` | `search_by_item_name()` — Chroma `where={"item_name": ...}` 완전일치 |
| `rag_prototype/rag_chain.py:42, 45` | `_build_context`가 이 완전일치를 1순위로 시도 |
| `rag_prototype/rag_chain.py:58` | 결과의 `SourceRef.item_name`에 전체 품목명이 그대로 노출됨 (사용자에게 보여지는 출처 표시) |

### ③ 검색 키워드 (부분일치, 짧아도 되는 곳) — 재검토 대상

| 파일:라인 | 내용 |
|---|---|
| `rag_prototype/mfds_client.py:35-37` | `search_by_name(item_name)` — 식약처 API 자체가 부분일치라 짧게 넣어도 됨 |
| `scripts/demo_e2e.py:34, 50` | `SAMPLE_DRUG_NAMES` — 처음엔 전체 품목명(`"타이레놀정500밀리그램"`)이었다가 짧게(`"타이레놀"`) 수정함. **다만 실제 매칭에 쓰이는 `target`(L50)은 API가 돌려준 진짜 전체 item_name을 그대로 쓰므로, 이 리스트 자체는 "검색할 때 어떤 키워드로 찾을지"용도일 뿐 매칭 로직에는 영향 없음** |

### ④ 사람이 읽는 문서/도움말 문구 (코드 동작엔 영향 없지만 "정책" 문장이라 합의 필요)

| 파일:라인 | 내용 |
|---|---|
| `README.md:40-41` | "약품명은 정확한 품목명 권장" + `--drug "타이레놀정500밀리그램"` 예시 |
| `rag_prototype/cli.py:52` | `--drug` help: "약품명 (정확한 품목명 권장)" |
| `rag_prototype/schemas.py:37-38` | `MedicationInput` 독스트링 — "상품명(제품명)일 수도, 성분명일 수도 있다" |

**결론**: 바뀔 수 있는 건 ③④뿐이고, ①②는 애초에 식약처 원본을 그대로 저장/대조하는 부분이라 "제품명 표기 기준"을 팀원과 어떻게 정하든 영향받지 않습니다.

### 참고: 처방전 제품명/성분명 표기 관련 법적 근거

- **소관**: 처방전 서식·기재사항은 보건복지부 소관 (의료법 시행규칙, 별지 제9호 서식)
- **핵심 조문 — 의료법 시행규칙 제12조 제1항 제2호**: "처방 의약품의 명칭(**일반명칭, 제품명이나 「약사법」에 따른 대한민국약전에서 정한 명칭**)·분량·용법 및 용량" — 셋 중 하나만 기재하면 되며, **성분명(주성분) 기재는 필수가 아니고 제품명만 기재해도 요건 충족**
- **대체조제 근거 — 약사법 제27조**: 의사가 상품명으로 처방해도 약사가 성분·함량·제형이 동일한 다른 의약품으로 대체조제 가능 (원칙적으로 환자 사전 동의 필요)
- **실무 시사점**: 대부분의 실제 처방전은 상품명(제품명)만 표기 → OCR이 상품명을 뽑아줄 가능성이 높고, 이는 MFDS `itemName`(품목명)과 매칭이 잘 되는 편. 성분명 처리는 드문 예외 케이스로 우선순위를 낮춰도 됨.

## 2. 오늘(2026-07-03) 프로토타입 기능 검증 범위

### ✅ 실제로 실행해서 확인된 것

1. 식약처 API 실호출(부분검색) — curl, `demo_e2e.py`, "낙센" 테스트 등 여러 번 성공
2. 필드별 청크 분할 → ChromaDB 저장 — 실제 20개 청크 저장 확인
3. **정확매칭 성공 경로** — `demo_e2e.py`에서 API가 준 정확한 전체 item_name을 넣었더니 7개 필드(효능효과·용법용량·경고·주의사항·상호작용·부작용·보관법) 전부 정확히 찾아옴 (TOP_K=3을 넘는 7건이 나온 것이 정확매칭이 작동했다는 증거)
4. **짧은 이름 → 폴백 경로** — "낙센"처럼 짧게 넣었을 때 정확매칭 실패 후 라이브 재조회(식약처 API 즉시 조회) + 유사도검색으로 3건 찾아옴 확인
5. OCR `MedicationItem`과 동일한 필드(`drug_name`/`dosage`/`frequency`/`diagnosis`/`drug_class`) 형태(dict)를 그대로 넣는 `generate_guide_from_medication()` 어댑터 동작 확인
6. dry-run 모드(OpenAI 키 없음) 전체 흐름 — `review_required=True`로 정상 표시
7. `pytest` 9개 전체 통과 (hallucination 방어 로직 포함: null/단일값/해시불가 값에 대한 방어, self-consistency 채점 등)
8. Opus(xhigh) 5라운드 리뷰에서 발견·수정한 실제 버그: 인용 없는 답변 통과 문제, null 값 크래시, 비-리스트 반환 크래시, 해시불가 값 크래시, `.env`가 `.gitignore`에 빠져 있던 보안 이슈

9. **(추가, 2026-07-03 OpenAI 키 발급 후) 실제 OpenAI 생성 경로 검증 완료** — `generate_guide_from_medication({"drug_name": "낙센", "dosage": "250mg", ...})` 실행 결과: self-consistency 점수 0.95, `review_required=False`, `source_refs` 3건 모두 실제 참고자료(낙센정/낙센연질캡슐 효능·용법) 기반으로 정상 인용됨. dry-run이 아닌 실제 GPT-4o-mini 생성 응답으로 처음 확인.

### ⚠️ 아직 검증 안 된 것

1. `mfds_client.fetch_page()` (전체 목록 대량 페이지네이션 수집) — 정의만 되어 있고 호출한 적 없음
2. `cli.py`의 `ingest`/`query` 서브커맨드 자체 — 내부 함수는 파이썬으로 직접 호출해 테스트했으나, `python -m rag_prototype.cli ...` 커맨드라인 자체는 실행 안 해봄 (내부 로직은 동일해 위험은 낮지만 인자 파싱은 미검증)
3. 대량/동시 요청, API 오류 상황(429 등) 대응 — 소량 테스트만 진행
4. self-consistency 3회 생성 시 실제로 답변이 갈리는 케이스(예: 정보가 애매한 약) — 지금까지는 항상 점수가 높게 나온 "잘 맞는" 케이스만 확인됨

### 한 줄 정리

**"짧은 이름이 들어와도 안전하게 근거자료를 찾아오고, 실제 LLM이 인용 기반으로 가이드를 생성한다"는 핵심 흐름은 실제 데이터로 검증 완료. 남은 건 대량 수집·커맨드라인 진입점·엣지케이스 정도.**
